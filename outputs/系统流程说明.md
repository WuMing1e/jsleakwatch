# JSLeakWatch 全流程说明

一句话：定时把一批站点的 HTML / JS 抓回来，用规则和外部工具找硬编码凭证，交给大模型复核真伪，只把可信的推送到飞书，全过程在控制台里可查、可干预。

主链路：

```
站点 → 调度 → 采集/发现 → 检测(多来源) → 落库与变更比对
     → AI 复核 → 误报门控 → 告警推送 → 控制台展示
```

---

## 1. 站点进入系统

- 单个新增，或批量新增（粘贴清单 / 读 txt；自动补 `https://`、按主机去重、跳过已存在、报告无效行）。
- 每个站点独立配置：巡检周期、采集范围（默认同源）、页面递归深度、资产上限、是否抓 sourcemap、是否探测常见配置入口、启用 / 暂停。
- 批量操作：勾选后批量启用 / 暂停 / 改周期 / 立即扫描 / 删除；工具条上另有全部立即扫描、全部暂停、全部恢复。
- 暂停的站点不会被调度，也不产生新告警。

## 2. 调度（`app/scheduler.py`）

- 每 tick（默认 5 秒）查一次 `enabled=1 AND (next_scan_at IS NULL OR next_scan_at <= now)`，按到期时间排序取一批入队。
- 站点并行度默认 3，可在设置里调（当前部署是 8）；队列最多堆积 `并行度 × 3`，避免一次性把上千站点全塞进内存。
- 一轮扫描结束重排 `next_scan_at`；失败按 `15 · 2ⁿ` 分钟退避，上限不超过站点自己的周期。
- 容量公式：`需要的并行度 ≈ 站点数 × 单站耗时 ÷ 巡检周期`。

## 3. 采集与资产发现（`app/fetcher.py`、`app/discover.py`）

- 从入口页面递归发现：`<script src>`、`modulepreload`、内联脚本、JS 里的动态 `import()`、webpack / Next.js chunk 映射、`sourceMappingURL`（含 `.map` 里的 sourcesContent）、常见配置入口（`/config.js` 等）。
- 只在授权范围内采集：默认同源；同一站点请求间隔 350ms、全局并发 6、单资产 5MB 上限。
- 增量策略：每轮仍会重新抓取资产，但内容 sha256 与上次一致、规则版本也一致时**跳过规则检测**（省 CPU，也避免重复告警）。三种情况强制重检：
  1. 资产内容变了；
  2. 规则版本变了（导入 / 增删 / 改等级）；
  3. 资产被标记 `recheck` —— 删除发现时自动打标，保证删掉的命中下一轮还能重新出现。

## 4. 检测：内置规则 + 外部工具并行

- 内置规则 78 条（严重 19 / 高危 34 / 中危 18 / 低危 3 / 提示 4），配套香农熵校验、关键词预过滤、占位符与代码路径过滤、重叠抑制、字符串拼接还原；支持导入 gitleaks TOML 规则与自建规则。
- 逐资产并联分析器（CLI 插件，如 JSHawk）：只跑"新增或内容变化"的资产，稳态开销接近零。
- 整站扫描器（如 JScanner2）：自带抓取，按站点调起一轮，结果并入同一套发现。
- 同一凭证被多个来源命中时只保留一条，记录来源归属：`builtin` / `cli:<名字>` / `<扫描器>` / `ai:semantic`。

## 5. 落库与变更比对

- 指纹 = `hash(规则ID | 站点ID | 命中值 sha256)`，同一站点同一凭证永远指向同一条记录。
- 新指纹 → `new`（告警候选）；已存在但状态是「已失效」→ 复现；本轮没再出现 → 自动转「已失效」。
- 默认**不落明文**：只存掩码（`LTAI...qW3F(len=24)`）+ sha256 + 上下文片段。
- 状态机：`new` 待确认 → `open` 已确认 / `false_positive` 误报 / `ignored` 忽略 / `resolved` 已失效。

## 6. AI 复核（可选，位置在"检测之后、告警之前"）

- 对新增发现逐条判定：真凭证 / 误报 / 公开密钥 / 待人工确认，带置信度、理由、影响与修复建议。
- 默认只发掩码值与上下文，明文不出本机；结果按内容哈希缓存（实测 14 条判定 0 次真实调用）；受单轮与每日调用上限约束。
- 高置信度误报可自动把状态标成「误报」。
- 语义补漏（默认关）：把资产内容发给模型找规则表达不出的硬编码，发送前先把已命中的密钥替换掉。

## 7. 误报门控（`app/gating.py`）

- 按来源统计历史误报率：判定数 ≥ 3 且误报率 > 60% 的来源进入预筛。
- 被预筛来源的发现，AI 未确认前不在列表里展示（避免噪声淹没真问题）。
- AI 判定为误报的发现默认也从列表隐藏，可在设置里关掉。

## 8. 告警推送（`app/notify.py`）

- 触发点：扫描跑完且本轮有 `new` / 复现的发现。
- 过滤链：**AI 判定为误报 → 丢弃**；等级低于最低推送等级（默认中危）→ 丢弃。
- 合并：不超过汇总阈值（默认 5 条）逐条发明细卡；超过则合并成一张按站点分组的汇总卡；单轮上限 20 条。
- 卡片：头部颜色随最高等级（严重=红 / 高危=橙 / 中危=蓝 / 低危·提示=灰）；明细卡是两列字段 + 掩码值 + 可点来源文件 + 上下文代码块 + 跳转按钮；汇总卡带等级统计与按站点分段。卡片上标注 AI 结论与置信度。
- 只有发送成功才写 `notified_at`；失败不会假装推过，跳过原因（等级不够 / 告警关闭 / 飞书错误码）都会写进事件日志，设置页底部还有一行「最近推送」直接看结果。
- 支持飞书自定义机器人 Webhook、企业自建应用（可指定群 / 人、可 @）、以及通用 Webhook。

## 9. 控制台

| 页面 | 主要能力 |
| --- | --- |
| 概览 | KPI、等级分布、30 天趋势、最近发现、站点健康度（均分页） |
| 监测站点 | 新增 / 批量新增、批量启停与改周期、全部暂停 / 恢复、单站立即扫描 |
| 泄露发现 | 多维筛选、批量改状态 / 删除、详情抽屉（上下文、AI 结论、备注、复核、生成规则） |
| JS 资产 | 资产清单、内容变更时间与指纹 |
| 检测规则 | 内置规则开关与等级、gitleaks 导入、自定义规则 |
| 系统设置 | 采集参数、飞书告警、AI 复核、误报门控、白名单、分析器、整站扫描器、运行环境 |

- 实时刷新走 SSE：侧栏状态与计数一直保持最新；出现新发现时刷新概览与发现页，扫描完成时只刷新概览页 —— 设置 / 规则这类表单页不会被后台事件重绘清空。

## 10. 排障速查：为什么没看到 / 没收到

| 现象 | 常见原因 | 怎么确认 |
| --- | --- | --- |
| 没收到告警 | 本轮没有新发现（老发现不重复推） | 事件日志「扫描完成: 新发现 0 条」 |
| 没收到告警 | 站点是暂停状态，压根没扫 | 站点列表状态列「已暂停」 |
| 没收到告警 | 等级低于最低推送等级 | 日志「等级均低于『中危』, 按设置未推送」 |
| 没收到告警 | AI 判定为误报，按规则不推 | 日志「已推送 N 条告警, 跳过 M 条 AI 判定为误报」 |
| 没收到告警 | 本轮条数超过阈值，合并成一张卡 | 「已推送 1 条告警」指的是 1 张卡片，里面可能有多条 |
| 列表里看不到 | 来源被误报门控预筛，或 AI 判为误报被隐藏 | 发现页「显示全部」；设置里看当前被预筛的来源 |
| 删掉后不再出现 | 资产内容未变 → 增量跳过检测 | 现在删除会自动打 `recheck`，下轮重扫即回来；历史删除的需重新打标或做一次全量扫描 |
| 推送失败 | Webhook 地址错 / 网关异常 | 设置页「最近推送」显示异常 + 飞书错误码 |

## 11. 数据落地

- 单机 SQLite（WAL），数据目录 `data/`，表：`targets` / `assets` / `findings` / `scans` / `events` / `settings` / `ai_cache` / `ai_usage`。
- 关键索引：`targets(enabled, next_scan_at)`、`findings(severity, status)`、`findings(rule_id, status)`、`assets(target_id, url)`。
- 规模参考：5000 站点 / 25 万发现时，调度 tick 0.3ms、发现列表 0.9ms、概览首页 250ms（有 5 秒缓存）。
